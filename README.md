# Utility Coach для Cache

Proof of concept для SCOPE.GG: разбор флешек игрока после матча в CS2 на карте Cache.

Для каждой флешки игрока система отвечает на три вопроса:
- сколько ослепления врагов в среднем даёт такой бросок;
- как часто он ослепляет своих;
- есть ли из той же зоны броска бросок, который статистически значимо лучше.

Факты считает код. LLM только пересказывает их понятным языком, а отдельная проверка сверяет
каждое число, зону и направление разницы в тексте совета с фактами. Результат — один
самодостаточный HTML-отчёт.

## Зачем

Обычный разбор утилити показывает, что произошло: «флешка ослепила 0 врагов». Игроку полезнее
знать, что было бы лучше. Поэтому в разборе нужны три вещи:
- ожидаемый эффект броска с этой позиции;
- сравнение с другими бросками из той же зоны на тысячах матчей;
- конкретная альтернатива с прицелом и честной оценкой неопределённости.

## Данные

Выгрузка из MongoDB (Python pickle, 1.57 ГБ): 10 000 матчей Premier/MM на Cache.

| | Количество |
|---|---|
| Смоки | 729 947 |
| Флешки | 643 914 |
| HE | 565 392 |
| Молотовы | 446 164 |
| Записей «игрок × матч» | 99 921 |
| Из них с рейтингом Premier | ~24% |

По каждой флешке известно, кого она ослепила, на сколько секунд и был ли ослеплённый убит.
96% игроков встречаются ровно в одном матче. Поэтому единица анализа — игрок в одном матче,
то есть разбор после матча, а статистическая опора — лайнапы с большим числом бросков, а не
история игрока.

## Как это работает

```
pickle ─► parquet ─► зоны карты ─► признаки ─► xFlash ─► лайнапы ─► findings ─► совет LLM ─► HTML
                                                        └► гипотеза о рейтинге ─────────────┘
```

1. **Безопасное чтение.** Pickle читается потоково. Распаковщик разрешает только два класса:
   `bson.int64.Int64` и `bson.objectid.ObjectId`. Любой другой глобал вызывает ошибку и не
   исполняется.
2. **Зоны.** KMeans делит карту на 24 зоны по точкам бросков и приземлений, высота учитывается
   с весом. Зоны, которые удалось уверенно опознать по карте плотности, подписаны каллаутами
   Cache (T spawn, A main, Mid, B main, A site, B site). Остальные показываются как «Зона N».
3. **xFlash.** Две модели LightGBM:
   - регрессия секунд ослепления врагов;
   - классификатор вероятности тимфлеша (ослепить тиммейта больше чем на 1 с).

   Валидация разбита по матчам: 20% матчей отложены в hold-out, на остальных GroupKFold(5).
   Обе модели сравниваются с двумя бейзлайнами: глобальным средним и средним по паре
   «зона броска → зона приземления».
4. **Лайнапы.** Лайнап — клетка сетки 120×120 юнитов одновременно по точке броска и по точке
   приземления, внутри группы «сторона + зона броска + тип броска» (стоя, присед, прыжок,
   с бега). Клетка становится лайнапом, если в ней не меньше 30 флешек из train-матчей. Всего
   получилось 2 606 лайнапов, медиана — 55 бросков.
5. **Альтернатива и значимость.** Для лайнапа игрока ищется лучший по итоговой оценке лайнап из
   той же зоны броска за ту же сторону. Итоговая оценка — секунды ослепления врагов минус 2 с
   за каждый тимфлеш, со сжатием к среднему зоны (empirical Bayes).

   Находка попадает в разбор, только если у обоих лайнапов n ≥ 30 и 95% ДИ разницы оценок
   (Δscore) лежит выше нуля. Проверка значимости идёт по сырым средним, ДИ строится с поправкой
   Бонферрони на число кандидатов, а стандартная ошибка считается по числу матчей.
6. **Findings.** Для игроков из hold-out матчей код собирает JSON с фактами: итоги матча,
   разобранные флешки, свой лайнап, альтернатива, разница. Вместо реальных ID игроки названы
   «Игрок A…E».
7. **Совет LLM и проверка.** Модель (OpenRouter, по умолчанию `deepseek/deepseek-v4.1-flash`)
   пишет совет только по этому JSON. Затем `faithfulness.py` проверяет текст:
   - каждое число должно совпадать со значением из findings (знак не важен, округлять нельзя);
   - каждая зона должна быть зоной этой карточки;
   - направление каждой названной разницы («больше» / «меньше», «безопаснее») должно
     совпадать со знаком в findings;
   - слова-числа вроде «треть» или «в два раза» отклоняются.

   Если проверка не пройдена, модель получает список ошибок и пишет ответ заново. Если не
   прошёл и второй ответ, основным становится шаблонный совет, а текст LLM сворачивается
   с пометкой.
8. **Отчёт.** `out/report.html` — один файл: стили встроены, картинки в base64, внешних
   ссылок нет. Есть тёмная тема и вёрстка под телефон.

## Результаты (полный прогон на 10 000 матчей)

**xFlash на hold-out** (129 617 флешек из 1 994 матчей, которых модель не видела):

| Модель | Секунды ослепления врагов: MAE | R² | Тимфлеш: AUC | Brier |
|---|---|---|---|---|
| LightGBM | **1.914** | **0.143** | **0.731** | **0.144** |
| Среднее по паре зон | 2.096 | 0.054 | 0.644 | 0.156 |
| Глобальное среднее | 2.214 | 0.000 | 0.500 | 0.164 |

Модель обходит оба бейзлайна, результаты кросс-валидации совпадают с hold-out в пределах 0.3%.
R² скромный, и это ожидаемо: позиций врагов в момент взрыва в данных нет. Поэтому модель
оценивает средний эффект броска, а не исход конкретной флешки. Самые важные признаки: время
в раунде, точка приземления, зона броска.

**Лайнапы.** У 1 448 из 2 573 лайнапов, для которых нашлась альтернатива, она значимо лучше
даже после поправки Бонферрони.

**Гипотеза о рейтинге.** Корреляция Спирмена считалась на 13 767 парах «игрок × матч» с
рейтингом и хотя бы 5 флешками:

| Метрика | ρ | 95% ДИ |
|---|---|---|
| Факт минус xFlash (ослепление сверх ожидаемого) | +0.069 | [0.052; 0.085] |
| Доля тимфлешей | −0.065 | [−0.081; −0.047] |
| Доля флешек с фрагом | +0.072 | [0.055; 0.089] |

Направления ожидаемые: у игроков с рейтингом выше флешки лучше и тимфлешей меньше. Но связь
очень слабая, поэтому метрики флешек дают информацию, которой в рейтинге почти нет.

**LLM-слой.** Построено 5 карточек. Все 5 советов прошли проверку: 4 с первой попытки, 1 со
второй. Во втором случае первый ответ назвал альтернативу «безопаснее», хотя тимфлешей у неё
больше. Проверка направления это поймала, и исправленный ответ прошёл. Реальные ID в данных,
отправленных в LLM, и в отчёте не найдены.

## Пример совета (карточка D, сокращено)

> За матч у тебя 11 флешек, 35.0 секунды ослепления врагов, 3 тимфлеша и 1 флеш-фраг.
>
> В раунде 12 на стороне T ты бросил из Зона 19 в Зона 9 стоя, и враги ослепли на 0.0 секунды.
> Твой лайнап в среднем даёт 0.4 секунды ослепления врагов, а альтернатива из той же зоны
> броска — тот же тип броска стоя, прицел yaw 152.6 и pitch -30.1, приземление в Зона 3 — даёт
> в среднем 3.5 секунды, то есть на 3.1 больше. До точки броска альтернативы 318 юнитов от
> твоей точки броска. При этом тимфлешей у альтернативы на 11 п.п. больше, чем у твоего
> лайнапа.

Рядом с текстом в карточке есть таблица с фактами по каждому лайнапу: n, 95% ДИ, прогноз
модели. Там же бейдж о результате проверки.

## Ограничения

- **Чего нет в данных.** Нет исхода раунда, экономики и позиций игроков вне событий гранат.
  Нет тика начала раунда, поэтому время в раунде отсчитывается приближённо, от первой гранаты.
- **Только флешки.** Смоки не измеряются. Урон HE и молотовов собран, но агрегаты по лайнапам
  в этой версии не сделаны.
- **Сравнение наблюдательное.** Разница между лайнапами смешивает позицию, место приземления,
  тип броска и ситуацию в раунде. Это не причинный эффект смены броска.
- **Альтернатива — в той же зоне, но не в той же точке.** Точка броска альтернативы бывает в
  сотнях юнитов от точки игрока, расстояние указано в карточке.
- **Средние оптимистичны.** У выбранной альтернативы среднее завышено эффектом отбора лучшего
  из многих (winner's curse). Прогноз модели показан рядом для сравнения.
- **Покрытие.** Лайнапы покрывают примерно половину флешек. Остальные броски попадают в
  клетки, где меньше 30 флешек, и рекомендаций для них нет.
- **Приближения в статистике:**
  - стандартная ошибка лайнапа приближает кластеризацию по матчам через число матчей;
  - ДИ корреляций с рейтингом предполагают независимость пар «игрок × матч».
- **Зоны.** Зоны построены кластеризацией по всем матчам, включая hold-out (без таргета).
  Подписана только часть зон.
- **Что проверка не покрывает.** Проверка ловит неверные числа, зоны и направление разниц.
  Качественные объяснения в тексте совета она не проверяет.
- **Охват.** Только Cache и только Premier/MM.

## Запуск

Нужен Python 3.13.

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
```

Положите `grenades_by_match_0726.list` в корень репозитория или укажите путь к нему в
переменной `UC_RAW`. Для советов LLM нужен ключ OpenRouter:

```powershell
Copy-Item .env.example .env
notepad .env   # open_router_key=...; при желании OPENROUTER_MODEL=...
```

Без ключа отчёт всё равно соберётся, но с шаблонными советами. Ключ нигде не печатается и не
логируется.

```powershell
.venv\Scripts\python -m utility_coach.run all
```

Полный прогон занимает 7–10 минут, большую часть — чтение pickle. Шаги можно запускать по
одному, каждый читает и пишет файлы в `data/`: `ingest`, `zones`, `features`, `model`,
`lineups`, `rating`, `findings`, `advise`, `report`. Для быстрой проверки:
`run ingest --limit 200`.

Если диск C: заполнен, перед установкой и запуском перенесите кэши на другой диск:

```powershell
$env:PIP_CACHE_DIR='D:\pip-cache'; $env:TEMP='D:\tmp'; $env:TMP='D:\tmp'; $env:MPLCONFIGDIR='D:\mpl'
```

## Тесты

```powershell
.venv\Scripts\python -m pytest
```

173 теста. Сырой датасет и сеть в них не используются: тесты работают на маленьких фикстурах,
вызовы OpenRouter подменены.

## Структура

```
utility_coach/
  config.py          пути и константы
  safe_pickle.py     безопасный потоковый читатель pickle
  ingest.py          pickle → parquet: throws, flash_victims, damage_events, players
  zones.py           KMeans-зоны, глоссарий каллаутов, карта зон
  zone_callouts.json подписи зон
  features.py        признаки и таргеты для каждой флешки
  model.py           xFlash: LightGBM против бейзлайнов
  lineups.py         лайнапы, сравнение, лучшая альтернатива
  stats.py           гипотеза о рейтинге
  findings.py        карточки игроков: факты в JSON, фильтр значимости, псевдонимы
  advisor.py         OpenRouter, кэш ответов, повтор с ошибками, шаблонный совет
  faithfulness.py    проверка чисел, зон и направления разниц в тексте
  report.py          сборка out/report.html
  templates/         Jinja2-шаблон отчёта
  run.py             CLI
tests/               pytest
data/, out/          производные данные и отчёт (не в git)
docs/design.md       спецификация: задача, данные, методология, критерии успеха
```

## Приватность

В LLM уходит только findings JSON с псевдонимами «Игрок A…E». Реальные `PlayerID` и `MatchID`
туда не попадают, это проверяют тесты. Датасет, `data/`, `out/` и `.env` не коммитятся.
