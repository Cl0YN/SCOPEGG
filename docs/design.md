# Utility Coach для Cache — дизайн PoC

Дата: 2026-10-25. Статус: на ревью. Срок реализации: 1–2 дня.

## 1. Задача

Тестовое задание SCOPE.GG (вакансия Data Scientist / ML Engineer): на датасете гранат
(10 000 матчей Premier/MM, карта Cache, CS2) сделать proof of concept того, как данные
помогают **рядовому пользователю** SCOPE.GG. Готовая фича не нужна, нужна проверенная идея
плюс честный список ограничений датасета.

**Пробел в продукте.** SCOPE.GG уже показывает счётчики по гранатам: flash time, урон от
гранат, число смоков. Цифры без контекста не говорят игроку, хорошо он играет или плохо и
что ему изменить.

**Идея.** Пайплайн считает, насколько полезна каждая флешка игрока, сравнивает её с тем, что
в среднем даёт этот лайнап, и находит лучшую альтернативу с той же позиции. LLM превращает
проверенные факты в понятный совет. **LLM только формулирует советы, все выводы пайплайн
считает и проверяет сам.**

**Критерии успеха:**
- модель xFlash на тестовых матчах обгоняет оба бейзлайна, валидация без утечки;
- для 3–5 игроков из тестовых матчей есть карточки советов, и каждое утверждение в них
  подкреплено числом из findings;
- доля верифицированных утверждений LLM измерена и показана в отчёте;
- ограничения датасета названы явно.

## 2. Данные (уже проверено)

- Файл `grenades_by_match_0726.list`: Python pickle (protocol 4), 1.57 ГБ, выгрузка из
  MongoDB. Верхний уровень — список документов, по одному на матч.
- 10 000 матчей с уникальными `MatchID`. 99 921 запись игрок-матч, `PremierRatingNew` есть
  примерно у 24% из них.
- Гранаты: smokes 729 947, flashbangs 643 914, HEs 565 392, fires 446 164.
- Поля флешки: `GeneralInfo` (`ThrowerID`, `Team` 2=T / 3=CT, `RoundIndexMatch`,
  `ThrowPoint{Position, Velocity, ViewX=yaw, ViewY=pitch, IsCrouching, IsAirborne}`,
  `PosFrom/PosTo`, `StartTick/EndTick`), `FlashedPlayers[]{PlayerID, Team, FlashDuration,
  FlashDurationAdded, ExistingFlashDuration, Position, ViewAngle, WasKilled{By, TickNumber,
  RemainingFlashDuration, OpenKill}}`.
- HE и молотовы: `DamagedPlayers[]{PlayerID, Team, Damage[]{HealthDamage, ArmorDamage,
  WasKilled}}`.
- **Игроки почти не повторяются между матчами.** На выборке из 3000 матчей 96% `PlayerID`
  встречаются ровно в одном матче. Медиана — 6 флешек на игрока за матч, p90 — 15.
  Отсюда единица персонального анализа: **игрок в одном матче** (разбор после матча).
  Статистическая опора — лайнапы с большим n, а не история игрока.
- `ProjectileID` уникален внутри матча. Среди записей `FlashedPlayers` много
  самоослеплений (~23%). У `WasKilled.By` не бывает самоубийств (`By ≠ PlayerID`).
- Чтение: безопасный потоковый Unpickler. Разрешены только глобалы `bson.int64.Int64` и
  `bson.objectid.ObjectId`, их заменяют локальные заглушки. Полный проход занимает
  около 3.5 мин. В RAM целиком файл не влезает: свободно около 2.9 ГБ.

## 3. Объём

**Входит:** флешки — это ядро (модель, лайнапы, советы). HE и молотовы — только агрегаты
урона по лайнапам, отдельной модели нет. *Обновление при реализации:* урон по HE и
молотовам собирается (`damage_events.parquet`), но агрегаты по лайнапам в этой версии
отложены; это указано в ограничениях отчёта.

**Не входит:** эффект смоков (данных о нём нет), интерактивный UI, другие карты.

## 4. Архитектура

Python-пакет `utility_coach/` в этом репозитории. Датасет и производные данные в git
не попадают.

```
utility_coach/
  safe_pickle.py   # безопасный потоковый читатель (whitelist глобалов)
  ingest.py        # pickle -> parquet: throws, flash_victims, damage_events, players
  zones.py         # кластеризация точек -> зоны карты + глоссарий каллаутов
  features.py      # таргеты и признаки на одну флешку
  model.py         # xFlash: LightGBM + бейзлайны, GroupKFold, hold-out, SHAP
  lineups.py       # лайнапы (зона броска + кластер приземления + тип броска), EB-сжатие
  findings.py      # факты по игроку -> JSON, фильтр значимости, анонимизация
  advisor.py       # OpenRouter LLM, кэш ответов, повтор с ошибками
  faithfulness.py  # проверка чисел и зон в ответе LLM
  report.py        # сборка HTML (Jinja2 + matplotlib base64)
  templates/report.html.j2
tests/             # pytest, фикстурный мини-pickle
data/              # gitignored: parquet, кэш LLM
out/               # gitignored: report.html
```

Поток данных: `pickle → ingest → parquet → zones → features → model + lineups → findings
(JSON) → advisor (LLM) → faithfulness → report.html`. Каждый шаг читает и пишет файлы в
`data/`, поэтому шаги перезапускаются независимо.

Окружение: venv, pip-кэш и временные файлы только на D:. Диск C: забит.

## 5. Зоны карты

- Точки бросков и приземлений всех гранат кластеризуются KMeans на 20–30 зон в плоскости XY;
  уровни Z различаем через порог.
- Строится карта плотности точек: 2.4 млн точек сами очерчивают геометрию уровня. Сторону
  карты определяем по броскам T и CT в начале раунда.
- Зоны подписываются каллаутами Cache вручную, по картинке. Если зону не удаётся опознать
  уверенно, она остаётся «Зона N», а в ограничениях это указано.
- Глоссарий `zones.json` хранит id зоны, каллаут и центроид. Он нужен для признаков, для
  промпта и для проверки faithfulness.

## 6. Признаки и модель xFlash

Единица — одна флешка (~644 тыс.).

**Таргеты:**
- `enemy_blind_s` — сумма `FlashDuration` по ослеплённым игрокам противоположной команды
  (регрессия, основной таргет).
- `teamflash` — ослеплён хотя бы один тиммейт, не сам бросающий, больше чем на 1 с
  (бинарный таргет).
- Описательные метрики, не таргеты: самоослепление; `flash_kill` — кто-то из ослеплённых
  врагов был убит. Команду убийцы не проверяем, поэтому редкие тимкиллы врагов попадают в
  счёт; это отмечено в ограничениях.

**Признаки** (только то, что известно о броске и полёте):
- точка броска xyz и зона;
- yaw и pitch;
- присед, прыжок, скорость игрока (|Velocity|, ~245 — бег);
- точка приземления xyz и зона;
- дистанция, время полёта;
- сторона, номер раунда, примерное время в раунде (от первой гранаты в этом раунде).

**Валидация:**
- 20% матчей уходят в hold-out (по `MatchID`), на остальных 80% 5-fold GroupKFold
  по `MatchID`;
- игроки для карточек берутся только из hold-out матчей.

**Модели:** LightGBM против бейзлайнов (глобальное среднее; среднее по паре
«зона броска → зона приземления»).

**Метрики:**
- MAE и R² для `enemy_blind_s`;
- ROC-AUC, Brier и calibration plot для `teamflash`;
- SHAP-важности признаков.

**Ожидание.** R² будет скромным: позиций врагов в момент взрыва в данных нет. Модель
оценивает средний эффект лайнапа, а не исход конкретного броска. В отчёте это
сформулировано явно.

## 7. Лайнапы и рекомендации

- Лайнап — клетка сетки 120×120 юнитов (`LINEUP_EPS`) одновременно по точке броска и
  по точке приземления, внутри группы «сторона + зона броска + тип броска (стоя / в
  приседе / прыжок / с бега)». Лайнапом клетка становится, если в ней не меньше 30
  train-флешек. Сначала был DBSCAN по приземлению, но на реальных данных он сливал
  точки цепочкой в кластеры до 41 тыс. флешек, у которых нет одного воспроизводимого
  броска. Test-флешка относится к лайнапу, если попадает в ту же клетку.
- Канонические параметры лайнапа — медианы позиции броска, yaw (круговая медиана) и pitch.
- Для ранжирования эффект лайнапа сжимается к среднему зоны (empirical Bayes). tau2
  оценивается одной на сторону по всем лайнапам. `score = blind_eb − TF_PENALTY_S·tf_eb`.
- Значимость проверяется по сырым средним. Разница `Δscore = Δblind − TF_PENALTY_S·Δtf`,
  её 95% ДИ строится с поправкой Бонферрони на число кандидатов K, из которых выбрана
  альтернатива. se считается по числу различных матчей в лайнапе — это консервативная
  поправка на зависимость флешек внутри матча. Находка значима, если нижняя граница ДИ
  Δscore больше 0.
- Рекомендация для флешки игрока: лучший по score лайнап из той же зоны броска и с той же
  стороны, если находка значима.

## 8. Гипотеза о рейтинге

Подмножество: пары «игрок × матч» с `PremierRatingNew` и не меньше 5 флешками в матче.
Метрики на маленьком n шумные, но пар много (~24 тыс. записей с рейтингом). Считаем
корреляцию Спирмена между рейтингом и каждой из трёх метрик:
- «факт − xFlash»;
- доля тимфлешей;
- конверсия `flash_kill`.

95% доверительный интервал получаем бутстрепом. Если связи нет, это тоже результат: метрика
измеряет что-то, чего не видно в рейтинге.

## 9. Findings → LLM

**Findings JSON** собирает код по одному игроку в одном матче (разбор после матча).
В JSON входят:
- описательные итоги матча: число флешек, секунды ослепления врагов, тимфлеши, флеш-фраги
  и перцентиль игрока среди всех пар «игрок × матч». Это контекст, не статистический вывод;
- находки по конкретным флешкам: раунд, зоны броска и приземления, фактический эффект,
  статистика лайнапа (xFlash, доля тимфлешей, n, ДИ 95%) и лучшая альтернатива из той же
  зоны (xFlash, доля тимфлешей, n, ДИ, yaw, pitch, тип броска).

Фильтры:
- находка по флешке попадает в JSON, только если у обоих лайнапов n ≥ 30 и разница
  значима: ДИ разницы не включает 0;
- топ-3–5 находок отбираются по размеру эффекта;
- `PlayerID` заменяется на «Игрок A/B/…».

**Советник:**
- OpenRouter, модель `deepseek/deepseek-v4.1-flash`, задаётся в `.env` через
  `OPENROUTER_MODEL`; ключ берётся из переменной `open_router_key` в `.env` (файл в
  gitignore, рядом лежит `.env.example`);
- temperature 0.2;
- системный промпт: контекст CS2 (роль флешек, тимфлеш, поп-флешки, стороны), глоссарий зон
  Cache и правило «только факты из JSON, без своих позиций, лайнапов и чисел»;
- ответы кэшируются в `data/llm_cache/` по хэшу промпта.

**Faithfulness:**
- из ответа достаются все числа и названия зон;
- каждое число должно совпадать со значением из JSON с допуском на округление до
  показанной точности; каждая зона должна быть из глоссария;
- если проверка не прошла, делается один повтор со списком ошибок; если и он не прошёл,
  карточка помечается «не верифицировано», и рядом показывается шаблонный совет;
- в отчёт идёт доля верифицированных утверждений.

**Деградация:** нет ключа или ошибка API (3 повтора с backoff) — отчёт собирается с
шаблонными советами, в отчёте написано, что LLM-слой отключён.

## 10. Отчёт

`out/report.html` — один самодостаточный файл. Разделы:
1. Задача и идея.
2. Датасет и ограничения.
3. Карта зон.
4. xFlash: валидация, калибровка, SHAP.
5. Гипотеза о рейтинге.
6. Карточки советов для 3–5 игроков: факты → текст LLM → статус проверки.
7. Оценка LLM-слоя.
8. Что дальше.

## 11. Ограничения датасета (войдут в отчёт)

- Нет исхода раунда, экономики и позиций игроков вне событий гранат, поэтому нельзя оценить
  влияние гранат на победу в раунде.
- Нет тика начала раунда: время в раунде приближённое.
- Эффект смоков не измеряется.
- Рейтинг есть только примерно у 24% записей игрок-матч.
- Игроки почти не повторяются (96% — один матч), поэтому историю игрока и его личные
  тренды не построить. Персональный разбор возможен только по одному матчу.
- Нет геометрии карты и каллаутов: зоны получены кластеризацией и подписаны вручную.
- Только Cache, только Premier/MM; на другие карты и уровни игры результат не переносится
  автоматически.

## 12. Тесты

pytest на фикстурном мини-pickle:
- `safe_pickle` блокирует посторонний глобал и читает Int64 и ObjectId;
- таргеты на вручную собранной записи: тимфлеш, самоослепление, flash_kill, enemy_blind_s;
- faithfulness ловит выдуманное число и выдуманную зону и пропускает корректный ответ;
- фильтр значимости findings отбрасывает находку с малым n или с ДИ разницы, который
  включает 0.
